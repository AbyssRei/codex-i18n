# Codex i18n 管理器技术选型

状态：交互式选型已完成；实现与验证进展以代码、测试和 README 为准。

## 目标与范围

- 面向 Windows，以 Rust 实现图形化管理器；分发目标为单个便携 EXE，运行时无需 Python。具体 Windows 版本、运行库和单文件部署效果须在目标环境验证。
- 从当前用户安装的 Store 版 `OpenAI.Codex` 创建完整的独立副本，在副本上修复 i18n 开关默认行为，保留 WindowsApps 原版。
- 创建名为 `ChatGPT(i18n)` 的 Windows 快捷方式，指向管理器的启动入口。该入口每次先检查 Store 包版本，再运行当前修复版。
- 版本不同时，展示当前修复版与 Store 包版本，提供“重新生成修复版”和“继续运行”。检查失败时说明原因，并允许用户决定是否继续运行已有副本。
- 系统浅色／深色模式为默认外观，并响应系统外观变化。

## 已确认的技术方案

| 用途 | 方案 | 说明 |
| --- | --- | --- |
| 语言与 GUI | Rust 2024、GPUI Kit | 界面使用 GPUI Kit 组件，启动和运行期间同步系统主题。 |
| Windows 集成 | `windows` crate，优先系统 API | 查询当前用户的包、验证签名、创建快捷方式及处理必要的进程状态。 |
| 修复定位 | `regex` 的字节匹配，加 Rust 变量一致性校验 | 匹配逻辑与参考脚本的 ASCII 字节语义一致；检查候选重叠情况，避免漏掉有效匹配。 |
| 数据格式 | `serde`、`serde_json` | 读取 ASAR 头部和维护本项目状态。 |
| 哈希 | `sha2` | SHA-256 流式计算，校验资源、分块及原始和修复后的文件。 |
| 错误处理 | 核心 `thiserror`；应用层 `anyhow` | 核心错误可分类，界面展示带上下文的错误。 |
| 后台任务 | 标准库专用线程、`async-channel`、GPUI 前台任务 | 后台处理阻塞文件工作；前台异步接收进度，负责更新 UI。 |
| 暂存 | `tempfile` | 在受管理目录和目标文件系统内创建临时文件、暂存目录；显式处理持久化和清理错误。 |
| CI 缓存 | `Swatinem/rust-cache` | 缓存 Cargo 依赖和构建产物，观察实际 CI 恢复和保存时间后调整。 |

这些库是直接使用的候选依赖；实现时重新核对其最新稳定版本和实际 API。直接依赖需要显式声明，即使它们已存在于 GPUI Kit 的间接依赖中。

## 核心流程

### 创建与更新副本

1. 查询当前用户的 `OpenAI.Codex` 包身份、四段版本号及安装路径。识别不到、发现多个不明确的候选或读取失败时给出错误，避免猜测。
2. 验证源 EXE 的 Windows 信任状态和预期签名者身份；验证 EXE 中记录的 ASAR 头哈希以及待修改资源的 SHA-256 和分块哈希。验证失败即停止。
3. 在用户可写、由本程序管理的目录内创建新的暂存版本，完整复制所需文件。默认位置建议为 `%LOCALAPPDATA%\CodexI18n`，最终路径及自定义能力在实现界面时确定。
4. 对暂存副本执行与参考脚本等价的修复：确认唯一匹配，保持资源长度和 ASAR 头长度，更新资源整体和分块哈希，并更新副本 EXE 中对应的 ASAR 头哈希。原脚本仅供参考，其附带的清理行为不视为本项目要求。
5. 重新验证修复后的文件和记录；在切换前再次检查源包身份与版本，确保生成期间 Store 应用未变化。
6. 在同一文件系统中持久化新版本和状态文件，仅在新版本完成验证后更新当前指向。临时文件替换和状态持久化要考虑失败恢复，不把单次文件重命名误认为跨多个文件的原子事务。
7. 取消和失败时不切换到未完成的新版本；保留现有可运行版本。仅清理本程序明确创建并可安全识别的临时内容，异常退出后可识别残留并安全处理。

复制、修补、验证和文件切换须处理运行中的修复副本，以及窗口关闭或取消的情况。取消采用协作式检查；进入状态切换阶段时应保护一致性，不能仅依靠丢弃线程或任务句柄。

### 快捷方式与启动

- 由 Windows Shell 创建名为 **`ChatGPT(i18n)`** 的快捷方式；快捷方式指向管理器并携带启动参数，不直接指向修复版 EXE，以确保每次启动都能检查。
- 记录修复版的来源包身份、Windows 四段版本及副本路径。Windows 包版本与本项目的 SemVer 版本分开处理。
- 包版本相同且副本状态可用时直接启动；不同时提供“重新生成修复版”和“继续运行”。更新成功后启动新副本，更新失败时保留旧副本并报告错误。
- 若安装包无法查询或副本缺失，应提示实际状态；允许继续运行仅适用于已存在且可运行的副本。
- 快捷方式的具体放置位置、安装或移动管理器后如何修复快捷方式，作为实现阶段需要明确和验证的细节。

## 依赖、版本与提交约定

- 实施时选择当时可用的最新稳定直接依赖；在 `Cargo.toml` 使用兼容版本要求，不使用精确版本约束。
- 将 `Cargo.lock` 纳入版本控制，CI 用锁文件构建；定期检查依赖新版本、升级并重新验证。间接依赖可能受到上游约束，不能保证整棵依赖树始终各自处于最新版本，GPUI Kit 的底层 GPUI 快照即为一例。
- 本项目从现有的 `0.1.0` 开始，遵循语义化版本。Windows Store 包的四段版本不是本项目的 SemVer。
- 提交使用约定式提交，例如 `feat: add portable build workflow`、`fix: preserve previous copy on update failure`。
- GitHub Actions 的 Marketplace Action 使用当时最新的主要版本标签，不锁定到精确版本或提交 SHA。实施时重新核对；主要版本变化不会由已有标签自动跟进。
- CI 在 Windows 上运行格式检查、静态检查、测试和 release 构建，并使用 Rust 缓存。缓存仅覆盖 Cargo 依赖和构建产物，不缓存用户安装的 Codex 或生成的副本。缓存缺失不应阻止构建；评估缓存命中、恢复和保存耗时。

## 验证与已知边界

- 为 ASAR 解析、匹配唯一性、变量不一致和重叠候选、资源完整性、路径约束、取消、失败恢复与版本比较提供测试；采用自造测试数据，不依赖 CI 安装 Store 版。
- 在本机对真实 Store 安装进行只读检查，并对独立副本执行端到端测试。CI 无法替代依赖 Windows Store 安装、签名和 GUI 的实际验证。
- 检查快捷方式目标、带空格和中文的路径、深浅主题、任务进度和桌面启动。验证程序及生成副本的运行库需求、Windows 版本和图形设备兼容性。
- 原脚本提示修补后的副本 EXE 签名失效且不具有 Store 包身份；相关 Windows 功能可能不同。正式版和副本可能共用用户数据，避免同时运行并验证实际行为。
- 原型实测及其局限记录在 `.prototypes/README.md`。现有样本不能证明未来上游版本仍符合当前匹配规则；匹配数量或完整性不符时必须停止而不是猜测修改。
